# TradePilot + Supabase setup

## Current state

The Supabase schema has been created in the linked **Genesis AI** project (`rqejcidqvfoihuhaqonv`). It adds isolated `tradepilot_*` tables and a private `tradepilot-teaching` Storage bucket without replacing the existing Genesis AI tables.

The current application code is **not connected to these tables yet**: `lib/db.ts` still reads/writes `data/db.json` and uploads files to the local filesystem. This matters on Vercel because local files are ephemeral and can be shared inconsistently across serverless instances.

## Supabase tables

- `public.tradepilot_users`: app users, password hashes, and roles (`user`, `teacher`, `admin`). This is the app's existing custom auth model; it is separate from Supabase Auth users.
- `public.tradepilot_teaching_cards`: teaching notes and extracted text, tags, creator, and Storage object path.
- `public.tradepilot_events`: registration, login, chat, and upload analytics.
- Storage bucket `tradepilot-teaching`: private file uploads (200 MiB max).

RLS is enabled on all three tables and direct `anon`/`authenticated` access is revoked. The intended integration is server-only database access using a Supabase secret/service-role key held in Vercel environment variables. Never expose that key in `NEXT_PUBLIC_*` variables or browser code.

## Vercel environment variables to add

- `SUPABASE_URL=https://rqejcidqvfoihuhaqonv.supabase.co`
- `SUPABASE_SERVICE_ROLE_KEY=...` (copy the server secret/service-role key from Supabase Project Settings → API Keys; do not paste it into chat or commit it)
- Keep `AUTH_SECRET` as a long random secret and keep `ADMIN_EMAIL` set to the intended first administrator email.
- Keep `ANTHROPIC_API_KEY` server-side if the chat API uses Anthropic.

Set these in Vercel → Project → Settings → Environment Variables for Production (and Preview/Development if required), then redeploy.

## Application code changes still required

1. Add the pinned dependency `@supabase/supabase-js` to `package.json` and commit the lockfile generated by a working npm environment.
2. Create a server-only Supabase client module (for example `lib/supabase-admin.ts`) using `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`; never import it into client components.
3. Replace the JSON-file functions in `lib/db.ts` with async database operations for user lookup/creation/role changes, event logging, and teaching-card CRUD. Because Postgres calls are async, update every caller to `await` the operations.
4. Update `lib/auth.ts` to await user lookups. Preserve bcrypt password verification, signed HttpOnly session cookies, and server-side role checks.
5. Update these files to use the database: `app/api/auth/register/route.ts`, `app/api/auth/login/route.ts`, `app/api/admin/users/route.ts`, `app/api/teach/cards/route.ts`, `app/api/teach/upload/route.ts`, `app/api/chat/route.ts`, `app/admin/page.tsx`, and `app/teach/page.tsx`.
6. Change teaching uploads from `fs.writeFileSync` to uploads into the private `tradepilot-teaching` Storage bucket. Save only the Storage object path in `tradepilot_teaching_cards`; serve downloads through an authenticated server route or short-lived signed URLs after checking the user's role.
7. Remove runtime dependence on `data/db.json` and local `data/uploads` after migration. Existing JSON data, if any, must be migrated deliberately before removal.
8. Add tests for registration/login, admin role changes, teaching access control, and user isolation; run `npm run build` in a working build environment before deploying.

## Important first-admin note

The current app promotes a user to admin when their email equals `ADMIN_EMAIL`. Preserve that only as a controlled first-admin bootstrap. Do not allow users to set their own role through registration or browser-submitted metadata. Once the first admin exists, restrict role changes to the admin API.
